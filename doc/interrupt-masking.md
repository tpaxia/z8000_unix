# Interrupt masking and user preemption

Date: 2026-10-05. Status: fixed and tested.

The diagnosis and original measurements below describe the old behavior.
The implemented fix and regression results are at the end.

## The problem

User programs run with both interrupt enables clear, and so does nearly all
kernel code. Interrupts are taken only in the idle loop and in the short
stretches after kernel code calls `spl0()` or `spl1()`, including
`sleep()`, the scheduler, and the clock handler.

Two consequences:

- A user program that loops without making a system call freezes the machine.
  Nothing preempts it, the keyboard is never read, and no other process runs.
- About 93% of clock ticks are lost in the measured boot workload, giving
  about fifteen times too few ticks. The slowdown of time of day, `sleep`,
  `alarm` and tty delays depends on how much each workload masks the clock.

The existing tests exercise blocking programs, and the kernel enables
interrupts while it sleeps. They do not test a syscall-free CPU-bound loop.

## Background

The Z8000 has two interrupt enables in the FCW: VIE (`0x1000`) for device
interrupts and NVIE (`0x0800`) for the clock. They take the place of the
PDP-11's priority levels; see Interrupt Levels in
[kernel-technical-reference.md](kernel-technical-reference.md).

## Where it comes from

The entry and return paths were incomplete, and the memory-access routines
also discarded interrupt state. All are code written for this port.

### 1. System calls enter the kernel with interrupts off

`syscall_entry` in `trap.s` switches from SEG+SYS to the mode the C code runs
in with

```
ld	r1, #0x4000	! FCW: NONSEG + SYS
ldctl	fcw, r1
```

`0x4000` has VIE and NVIE clear, and nothing sets them before `trap()` is
called. The interrupt stubs (`nvi_entry`, `vi_entry`) load the same value,
which keeps their initial entry masked. Device handlers can subsequently
allow the clock; syscall C code should normally run with both enables set.

V7 does the opposite. In `usr/sys/conf/mch.s` the trap path goes through
`call1`, which executes `spl 0` before calling `trap()`; only the interrupt
path (`call`) keeps the priority it was entered at.

### 2. User mode is entered with interrupts off

`_retu` in `krt.s` builds the IRET frame that starts the first user process
with

```
push	@r14, r0		! FCW: NONSEG+NORM = 0x0000
```

`0x0000` also has both enables clear. Every later process inherits this FCW:
`fork` copies the parent's saved trap frame and `exec` keeps it.

### 3. Nothing reschedules on the way back to user mode

The clock and `wakeup()` set `runrun` to ask for a reschedule. Nothing reads
it: it appears in `sys/clock.c` and `sys/slp.c` only.

V7 checks it in two places, and this port has neither:

- at the end of `trap()` in `sys/trap.c`: `if (runrun) qswtch();`
- in `mch.s`, after an interrupt handler returns to user mode: `tstb _runrun`,
  and if it is set, a call to `trap` with the "give up cpu" code.

So even with interrupts enabled, a running process would never be preempted.

### 4. Memory access and fork keep interrupts masked

`fubyte`, `fuword`, `subyte`, `suword`, `copyin`, and `copyout` switch to
SEG+SYS for user-memory access, then load `0x4000` on return to NONSEG+SYS.
They discard the caller's interrupt enables. Enabling only syscall entry
would therefore leave much of the kernel masked again.

`copyseg()` also masks the entire 64 KB copy during fork. The 4 KB u-area
copy in `newproc()` has the same issue on a smaller scale. The MMU copy
window must be protected, but interrupts can run between short copies once
its identity mapping is restored.

## Original measurements

Taken from the emulator's instruction trace of the boot test
(`cmake --build build --target test`, 39,401,386 cycles).

| Mode | Interrupt enables | Share of instructions |
|------|-------------------|-----------------------|
| Kernel | both off | 96.8% |
| Kernel | devices only | under 0.1% |
| Kernel | both on | 2.5% |
| User | both off | 0.7% |
| User | on | 0% |

| Event | Count |
|-------|-------|
| Clock ticks generated by the emulator | 7,871 |
| Clock interrupts taken (`nvi_entry`) | 537 |
| Device interrupts taken (`vi_entry`) | 118 |
| System calls (`syscall_entry`) | 102 |

The driver injects one tick per execution slice, requesting 5,000 cycles
per slice. Instructions can overshoot that budget, and HALT ends a slice
early, so dividing total cycles by 5,000 does not give the exact tick count.
The original figure of 7,880 was that estimate; 7,871 is the measured count.

The emulator latches an interrupt request in a single bit, so ticks that
arrive while the clock is masked merge into one. That is how 7,871 generated
ticks result in only 537 serviced interrupts (with a request also possibly
pending at the end).

### A looping program

A program consisting of `main() { for (;;) ; }` was built against
`tools/libc`, put in a copy of the root filesystem, and started from the
shell with the run limited to 120,000,000 cycles.

| | |
|---|---|
| Instructions traced | 19,053,748 |
| Last kernel-mode instruction | number 4,019,461 |
| User-mode instructions after it | 15,034,287 |
| Kernel entries of any kind after it | 0 |

Before that point the run took 415 clock and 89 device interrupts; 25 and 3
of them came after the program's last system call, in the instructions before
the kernel returned to it. From then on there are no clock interrupts, no
device interrupts and no system calls for the remaining three quarters of the
run.

## Implemented fix

- `_retu` starts user mode with FCW `0x1800`. Its stack-segment preparation
  is masked before changing R14 or NSPSEG.
- `syscall_entry` enters C with FCW `0x5800`. NVI enters C at `0x4000`;
  VI enters C at `0x4800`, blocking devices while allowing the clock.
- User-memory helpers save and restore the caller's FCW. Copy loops restore
  it between bytes, including when the caller deliberately had interrupts off.
- `trap()` and interrupt return share `userret()`, which delivers pending
  signals, updates priority, and calls `qswtch()` when `runrun` is set.
  Only interrupts returning to user mode take this path. The saved user SP
  stays on the process's kernel stack across switches, and the final check
  through IRET is masked. Requests are rechecked after a switch.
- Syscall dispatch now saves `u_qsav`, as V7 does, so an interrupted
  `sleep()` can unwind to the syscall return path. V7's `setrun()` handling
  of an existing wait channel is restored: a sleeper is unlinked before
  its link field is reused for the run queue.
- `spl4`/`spl5` clear VIE and set NVIE. This permits clock nesting while
  blocking device reentry. `BASEPRI()` tests the interrupted FCW: either
  enable clear means above base priority, so nested ticks defer callout
  execution and once-per-second processing. `clock()` also calls `spl1()`
  during its once-per-second work; it was never masked for that whole path.
- Both fork copies restore the MMU window and caller's mask between 16-byte
  chunks. `u_procp` continues to name the running parent during copying;
  the child installs its own process pointer when its saved context resumes.

This preserves the V7 model: kernel code can be interrupted, but interrupt
return does not preempt kernel code. Process switches happen at explicit
sleep/switch points and on return to user mode.

## Verification

From `v7z8000/usr/sys`:

```sh
cmake --build build --target test test-libc test-preempt
```

All pass. `test-preempt` builds a separate filesystem and checks:

- Three rounds of a syscall-free spinning child, with the parent regaining
  the CPU and killing it. Child user-time accounting must prove it actually
  ran for at least one second; killing a child before it runs cannot pass.
- An alarm terminating a syscall-free loop.
- A signal terminating a child blocked in a pipe read, exercising syscall
  unwinding and removal from the sleep queue.
- Two computing children checking live counters and stack data across
  interrupts and process switches.
- A console reader waking while its child spins. The driver waits for an
  output marker and another 100 ticks before sending input. The reader
  kills and reaps the child, prints its verdict, and returns to the shell.

The original boot transcript still passes, and `test-libc` reports all 33
checks passing. A negative-control kernel with user interrupts disabled
fails the new preemption test at its cycle limit.

The fixed boot trace has 72,954,670 cycles, 14,579 generated ticks and
14,556 clock entries. Direct latch instrumentation resolves the difference:
22 pulses merge before the first shell prompt, and one request is pending
at shutdown. The approximately 0.16% difference is **not a steady-state
loss rate** and must not be extrapolated into seconds lost per hour.
The trace also has 121 device entries and 102 syscalls. The increased cycle
count includes servicing the clock and restoring mappings between copy chunks.

This change does not implement user signal-handler trampolines; the port's
existing limited handling of caught signals is unchanged. The signal tests
use default termination actions.

## Measuring sustained clock delivery

The test driver observes the NVI pending bit before each pulse: an already
set bit means that pulse merges with an outstanding request. It independently
counts actual NVI dispatches when the CPU loads that vector's FCW, without
changing CPU execution or kernel code. Every run verifies:

```
generated = accepted + merged + pending
```

`-n` starts a fixed-length sample after an output marker (`-M`, default the
first shell prompt), and accounts for pending requests at both boundaries:

```
accepted_delta = generated_delta - merged_delta + pending_start - pending_end
```

The measurement ends before injecting another pulse, after the last pulse
has had an execution slice in which to be accepted. Idle HALTs do not end
measurement mode. A cycle limit remains as a failure watchdog.

Reproduce from `v7z8000/usr/sys/build` after building `test_driver` and
`preempt_image`:

```sh
./test_driver -c 20000000000 -n 2160000 -i ''
./test_driver -c 20000000000 -n 2160000 -d hd-preempt.img \
  -i 'preempttest console\n' -M 'preempt: waiting for input'
./test_driver -c 20000000000 -n 2160000 -d hd-preempt.img \
  -i 'while :; do preempttest; done\n' \
  -x 'preempt: scheduling, signals and context passed'
```

At `HZ=60`, 2,160,000 generated pulses represent ten hours of nominal timer
time. This harness injects after each requested 5,000-cycle slice (or early
HALT), not from an emulated 8253. These are measurements of this kernel and
test machine, not calibrated M20 hardware or host wall-clock measurements.

Results (2026-10-05), excluding everything before each start marker:

| Workload | Generated | Accepted | Merged/lost | Pending at either boundary |
|----------|----------:|---------:|------------:|---------------------------:|
| Idle shell | 2,160,000 | 2,160,000 | 0 | 0 |
| Syscall-free spinning child, parent blocked on console | 2,160,000 | 2,160,000 | 0 | 0 |
| Repeated preemption suite: fork/exec, syscalls, signals, pipes, context switches | 2,160,000 | 2,160,000 | 0 | 0 |

The repeated suite completed 66 full successful iterations during the run.
All three runs retained exactly the same 22 pre-sample merged pulses;
no further merges occurred. The ordinary
boot and both preemption regressions also passed with their prior cycle
counts unchanged. No sustained tick loss was observed in these workloads;
the previous estimate of about six seconds per hour is unsupported.
