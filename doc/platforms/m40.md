# Porting to the Olivetti M40: notes

Feasibility notes only: there is no implemented M40 kernel configuration. Start with the [common porting guide](porting-guide.md).

A first assessment of whether the Olivetti L1 M40 would be an easier target
for this port than the Olivetti M20. It is based on reading this project's
documents and on what is known of the M40 from its MAME emulation; nothing
here has been tried.

## Short answer

The M40 is a better target than the M20 because it has a real, programmable
MMU (a Zilog Z8010). It is not the MMU this port is written for, so it is not
a drop-in: the two places where the kernel depends on paging have to change.

## What the port assumes today

From `README.md`, `z8001_mmu_design_notes.md` and `step8-fork-mmu.md`:

- The kernel and user programs run non-segmented, each inside one 64 KB
  segment.
- The segment number selects a per-process map, so context switches are free
  and the kernel reaches user memory by using the process's segment number.
- The MMU is a custom paged one that exists only in the emulator: 2 KB pages,
  32 per segment.
- Two things depend on paging specifically:
  - the u-area and kernel stack sit at a fixed address (`0xF000`) in the
    kernel's segment and are swapped per process by remapping two pages
    (`UPAGE`, the KDSA6 equivalent);
  - a copy window (`WPAGE`) remaps two more pages so `newproc()` can write
    into the child.

## M20 versus M40

| | M20 | M40 |
|---|---|---|
| Mapping | Fixed, in PROMs | One Z8010: 64 segments, each with a programmable base, limit and attributes |
| Placing a process | Only in the segments the PROMs define | Anywhere in RAM, in 256-byte steps |
| Protection | None | Limit checks, system-only and read-only attributes, segment trap with violation status |
| Stack growth | Nothing to trap on | Downward-growing segment attribute and write-warning zone, which suit V7's `grow()` |
| Segment number per process | Limited to the PROM's segments | Up to 64, so "free context switch" and "kernel uses the user's segment number" carry over |
| RAM | 512 KB | 2 MB |
| Remapping part of the kernel segment | Not possible | Not possible: a Z8010 segment is one contiguous block |
| Hardware available | Real machine and an FPGA implementation | MAME only |

Base plus limit is also V7's native memory model: the PDP-11 kernel allocates
contiguous core and swaps whole processes.

## What would need rework on the M40

- **The u-area.** With a non-segmented kernel, `u` has to live in the
  kernel's own segment, and the Z8010 cannot redirect part of a segment. See
  the options below.
- **The copy window.** Not needed: a short segmented-mode assembly routine
  can copy between two segments directly.
- **The allocators in `machdep.c`.** From page frames to contiguous
  base/limit regions.
- **Size.** There is no split of code and data, so a non-segmented kernel
  (about 47 KB of text and data at present) plus its bss must fit in one
  64 KB segment.
- **Drivers.** Console on the GO252 video/keyboard board, a disk driver for
  the GO280 floppy or GO363 hard-disk controller, and the 8253 clock. None
  exist yet. The M20 work already boots a test kernel through the BIOS disk
  call.

## Options for the u-area

### 1. Keep the kernel non-segmented and copy

On each context switch a small assembly routine, using segmented addressing,
copies the u-area and kernel stack out to the old process and in from the new
one. Slower per switch, but it needs no compiler work and no change to the V7
sources, and it works on the M20 as well. This port has never run that way:
processes and the paged MMU arrived together in Step 8, whose notes list "no
bcopy of u-areas" as a property of the paged design. So the copying routine
would be new code, not a return to an earlier stage.

### 2. Run the kernel segmented

With 32-bit segmented pointers the kernel can address any segment, so `u` and
the kernel stack can live in a segment of their own at a fixed segment
number. Switching process means rewriting that one segment's base in the
Z8010: the direct equivalent of `mov r0, KDSA6`.

What else it gives:

- kernel code and data can be in separate segments, removing the 64 KB limit;
- the kernel can point at any process's segment from C;
- user programs can stay non-segmented, one segment each.

What it costs:

- **Compiler and assembler.** The PCC back end generates 16-bit-pointer code
  only, and its assembler (`az8`) does not assemble segmented instructions
  either: the two segmented files in the kernel, `rom.s` and `trap.s`, are
  assembled with GNU `z8k-coff-as`. (The remark in `PCC-Research.md` about an
  assembler that supports segmented modes is about ACK's, which this project
  no longer uses.) A segmented kernel needs a "large model" code generator
  (32-bit pointers, 4-byte return addresses, segmented calls) and segmented
  support in `az8` and the linker, or the GNU tools for all of it.
- **V7 source.** `sizeof(char *)` becomes 4 while `sizeof(int)` stays 2, and
  V7 kernel code mixes ints and pointers. This is the reason the project went
  non-segmented, and the project rule is not to modify V7 sources to work
  around the toolchain.
- **Size and speed.** Every pointer and call gets bigger and slower.

## Precedent: ZEUS on the Zilog System 8000

ZEUS, Zilog's own Unix for the Z8001 with Z8010 MMUs, takes option 2. From
the ZEUS 3.21 kernel headers (`sys/param.h`, `sys/user.h`, `sys/mmu.h`,
`sys/proc.h`):

- The kernel is segmented: `caddr_t` is a 32-bit `char *`, and `saddr_t`
  splits a pointer into segment and offset halves.
- `# define UBASE 0x3E00F400 /* kernel virtual addr of user struct */`: the
  user structure is at a fixed kernel virtual address, segment `0x3E`, offset
  `0xF400`. `user.h` declares `extern struct user u;`.
- `# define USIZE 12 /* size of PPDA (user struct)(clicks) */`: with 256-byte
  clicks that is 3072 bytes, exactly `0xF400`–`0xFFFF`. The comment in
  `user.h` says the block "resides at virtual kernel loc 0xF400" and
  "contains the system stack per user"; `u_stack` is the kernel stack,
  growing down from the top of the block.
- `proc.h` has `p_addr`, "address of swappable image", in clicks.
- The user structure also holds the process's own segment descriptors
  (`u_nsucode`, `u_segmts[NUSEGS]`), each a `struct segd` of base, limit and
  attribute, which is the Z8010 descriptor format.

So in ZEUS the per-process data area and kernel stack are one block in a
dedicated kernel segment at a fixed virtual address. The headers do not show
the context-switch code itself, but the layout implies it rewrites that
segment's descriptor to point at the new process's block.

The System 8000 has three Z8010s (code, data and stack). The M40 has one,
which is enough for this scheme: it needs one segment for the u-area, the
kernel's segments, and one segment per process.
